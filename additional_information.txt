Architektonisches und Mathematisches Design für Dynamische Schild-Rendermechaniken in NeoForge 1.211. Einleitung und Architektonischer RahmenDie Entwicklung prozeduraler 3D-Rendersysteme innerhalb der modifizierten Minecraft-Engine erfordert eine hochgradig präzise Abstimmung zwischen autoritativer Server-Logik, asynchroner Netzwerk-Synchronisation und GPU-beschleunigter Shader-Mathematik. Das vorliegende Dokument liefert eine erschöpfende Analyse und ein tiefgreifendes Konzept für die Implementierung eines dynamischen, reaktiven Energieschild-Systems innerhalb einer komplexen Raumschiff-Modifikation für NeoForge 1.21.Das modulare Raumschiff-System basiert auf einer strikten Model-View-Controller (MVC) Architektur, bei der die logische Autorität über Schiffsbewegungen, Energieverwaltung und Schildkollisionen vollständig vom Server getragen wird. Der Server nutzt fortschrittliche Java 21 Virtual Threads im ShipMorphologyService, um die volumetrische Dilatation des Schild-Meshes asynchron zu berechnen, ohne den Main-Thread zu blockieren. Dieses statische Mesh wird an den Client übertragen und dort in einem VertexBuffer (VRAM) vorgehalten.Die primäre Herausforderung besteht nun darin, diesem statischen VBO (Vertex Buffer Object) dynamisches visuelles Feedback zu verleihen, ohne die CPU-GPU-Bandbreite durch kontinuierliche Mesh-Neuberechnungen zu überlasten. Das System muss zwei visuelle Kernanforderungen erfüllen: Erstens eine organische, globale Farbanpassung des Schild-Meshes auf Basis des prozentualen Energiestatus, und zweitens einen ausbreitenden kinetischen Impuls (Impact Ripple Effect), der von dynamischen Einschlagstellen ausgeht. Um dies zu realisieren, wird die Blaze3D-Engine durch Custom Core Shaders in OpenGL 150 (GLSL) erweitert. Darüber hinaus adressiert dieser Bericht die kritischen Backend-Herausforderungen der NeoForge 1.21 Architektur, insbesondere das Multi-Impact-Handling zur Darstellung simultaner Treffer sowie die performante Event-Synchronisation über das moderne CustomPacketPayload- und StreamCodec-System.2. Mathematisches Design der Schild-Kolorierung (GLSL)Das Rendering prozeduraler Hexagon-Schilde in OpenGL 150 erfordert eine konsequente Trennung von räumlicher Vertex-Transformation und per-Pixel Fragment-Kolorierung. Da das Hexagon-Muster und die grundlegende Transparenz bereits funktional sind, fokussiert sich das Design auf die Manipulation der RGB-Farbkanäle in Abhängigkeit von globalen Uniform-Variablen, ohne den etablierten Alpha-Kanal des Musters zu kompromittieren.2.1 Farbraum-Metriken und Globale FarbmischungDie Farbe des Schildes fungiert als der primäre visuelle Indikator für den Spieler, um den Zustand des Raumschiff-Reaktors in Sekundenbruchteilen zu erfassen. Der Energiestatus wird dem Shader als normierter Float-Wert (u_EnergyLevel) zwischen $0.0$ (leer) und $1.0$ (voll) übergeben. Eine naive lineare Interpolation (mix()) zwischen drei primären Farbwerten im RGB-Raum führt unweigerlich zu sogenannten "matschigen" oder ausgewaschenen Übergangszonen, da die Helligkeitswahrnehmung des menschlichen Auges nicht linear verläuft.Um C1-stetige, satte Farbverläufe zu garantieren, wird die Interpolation durch hermitesche Polynome, spezifisch die smoothstep-Funktion, moduliert. Dieses Vorgehen verschiebt die Mischungsgewichte derart, dass die reinen Kernfarben über einen breiteren Energiebereich stabil bleiben und die Übergänge konzentrierter stattfinden.Es werden drei primäre Energiezustände und korrespondierende Farbvektoren definiert:Optimal ($1.0$ bis $0.5$): Ein hochenergetisches, kühles Cyan (vec3(0.1, 0.9, 1.0)).Kritisch ($0.5$ bis $0.2$): Eine destabilisierte Gelb-Lila-Mischung (vec3(0.9, 0.7, 0.2)).Versagen ($< 0.2$): Ein bedrohliches, tiefes Rot (vec3(1.0, 0.1, 0.1)).Die mathematische Verknüpfung dieser Zustände erfolgt kaskadierend. Zuerst wird der Übergang zwischen dem kritischen und dem Versagens-Zustand berechnet, anschließend wird dieses Zwischenergebnis mit dem optimalen Zustand interpoliert.2.2 Simulation von Organischer Instabilität (Flicker-Noise)Wenn die Schildkraft unter den kritischen Schwellenwert von 20 % fällt, soll die Struktur visuell zu versagen beginnen. Ein rein statisches Rot transportiert keine Dringlichkeit. Daher wird die Zeit (u_GameTime) genutzt, um die Luminanz der roten Farbe zu modulieren. Ein reiner Sinus-Oszillator wirkt jedoch zu mechanisch. Um organische Instabilität zu simulieren, wird eine stochastische Komponente (Pseudo-Random Noise) eingeführt.Die Flacker-Funktion $F(t)$ definiert sich als:$$F(t) = \max\left(B_{min}, \left( \sin(t \cdot \omega) \cdot 0.5 + 0.5 \right) \cdot \text{noise}(\lfloor t \cdot \rho \rfloor) \right)$$Wobei $t$ die kontinuierliche Spielzeit ist, $\omega$ die fundamentale Oszillationsfrequenz (z.B. $20.0$), $B_{min}$ das garantierte Minimum an Helligkeit (um völlige Unsichtbarkeit zu vermeiden), und $\rho$ die Frequenz des Rauschens (Sample-Rate der Störung). Die Funktion noise() generiert deterministische, pseudozufällige Werte basierend auf der fragmentierten Sinus-Hash-Methode.2.3 GLSL-Implementierung der FarbanpassungDer folgende GLSL-Code demonstriert die Integration dieser mathematischen Konzepte in den Fragment Shader. Durch die Kapselung der RGB-Logik in einer separaten Funktion wird sichergestellt, dass die spätere Alpha-Berechnung (Transparenz) strikt orthogonal zur Kolorierung verbleibt.OpenGL Shading Language// Uniforms, synchronisiert vom ClientShipState
uniform float u_EnergyLevel; // 0.0 bis 1.0
uniform float u_GameTime;    // Kontinuierliche Zeit (in Ticks oder Sekunden)

// Statische Farb-Vektoren (SRGB Farbraum)
const vec3 COLOR_OPTIMAL  = vec3(0.1, 0.9, 1.0);
const vec3 COLOR_CRITICAL = vec3(0.9, 0.7, 0.2);
const vec3 COLOR_FAILURE  = vec3(1.0, 0.1, 0.1);

// Deterministische Hash-Funktion für Pseudo-Zufall
float hash(float n) {
    return fract(sin(n) * 43758.5453123);
}

vec3 calculateEnergyColor(float energy, float time) {
    // Hermitesche Interpolationsgewichte für nicht-lineares Blending
    float blendOptimalCritical = smoothstep(0.4, 0.8, energy);
    float blendCriticalFailure = smoothstep(0.15, 0.4, energy);
    
    // Berechnung der Instabilität für niedrige Energiezustände
    float baseFlicker = (sin(time * 20.0) * 0.5) + 0.5;
    // Diskretes Samplen des Noises für "Zucken" anstatt fließender Übergänge
    float chaoticNoise = hash(floor(time * 15.0));
    float failureIntensity = max(0.3, baseFlicker * chaoticNoise);
    
    // Modulierte Versagens-Farbe (Helligkeit schwankt, kann leicht über 1.0 für Bloom gehen)
    vec3 animatedFailureColor = COLOR_FAILURE * (1.0 + (failureIntensity * 0.5));
    
    // Kaskadierende Farbmischung
    vec3 lowerTierMixed = mix(animatedFailureColor, COLOR_CRITICAL, blendCriticalFailure);
    vec3 finalBaseColor = mix(lowerTierMixed, COLOR_OPTIMAL, blendOptimalCritical);
    
    return finalBaseColor;
}
Diese Implementierung liefert einen extrem performanten, branch-freien (keine if-Statements) Pfad auf der GPU, was die Ausführungszeit pro Pixel minimiert.3. Räumlich-Zeitliche Wellenausbreitung: Der Impact Ripple EffectWenn das Energieschild kinetische oder thermische Energie absorbiert (Kollision, Explosion, Laser), soll eine visuelle Schockwelle über die Geometrie wandern. Die Komplexität dieser Anforderung ergibt sich aus der Tatsache, dass das Raumschiff sich kontinuierlich durch die Welt bewegt. Eine Wellenberechnung im World-Space würde dazu führen, dass der Einschlagpunkt im Raum stehen bleibt, während das Schiff durch ihn hindurchfliegt, was eine massive Verzerrung des Effekts zur Folge hätte.3.1 Koordinatensystem-Transformation und DistanzmetrikUm den Effekt an das Schiff zu "binden", muss die Metrik zwingend im Local-Space (Relativ zum AnchorPos oder Controller-Block des Schiffes) evaluiert werden. Der Vertex-Shader (VS) erhält die rohen Vertex-Positionen, die bereits relativ zur Modellmatrix des Schiffs vorliegen. Indem die untransformierte Objekt-Position als out vec3 v_LocalPos; an den Fragment-Shader (FS) weitergereicht wird, erhält jeder Pixel eine statische Koordinate relativ zum Schiffs-Anker.Der Einschlagpunkt ($P_{impact}$) wird folglich ebenfalls vom Server im Local-Space berechnet und an den Shader als Uniform übergeben. Die Euklidische Distanz $d$ für einen beliebigen Fragment-Punkt $P_{frag}$ lautet:$$d = \sqrt{(P_{frag.x} - P_{impact.x})^2 + (P_{frag.y} - P_{impact.y})^2 + (P_{frag.z} - P_{impact.z})^2}$$In GLSL wird dies hochoptimiert über die intrinsische Funktion length(v_LocalPos - u_ImpactPos) abgebildet.3.2 Die Kinetische Wellenfunktion (Wave Equation)Ein einzelner Impact-Ripple wird als konzentrischer, sich ausdehnender Ring modelliert, dessen Amplitude über Raum und Zeit abklingt. Die Welle wird definiert durch das Zusammenspiel einer Ausbreitungsfunktion (Wellenfront), einer Formfunktion (Dicke des Rings) und zwei Dämpfungsfunktionen (räumlich und zeitlich).Der Radius der Wellenfront $R(t)$ wächst linear mit der Zeit $t$ seit dem Einschlag:$$R(t) = v_{wave} \cdot t$$wobei $v_{wave}$ die Ausbreitungsgeschwindigkeit in Blöcken pro Sekunde ist.Die Form der Welle wird durch eine modifizierte Gaußsche Glockenkurve um den aktuellen Radius herum modelliert, um einen organischen, weichen Ring zu erzeugen:$$W(d, t) = \exp\left(-k_{width} \cdot (d - R(t))^2\right)$$Um zu verhindern, dass die Welle unendlich über das gesamte 100-Block lange Schiff wandert, greift die räumliche Dämpfung $D_{space}(d)$ basierend auf der inversen Exponentialfunktion, und die zeitliche Dämpfung $D_{time}(t)$, die den Effekt nach einem Maximum $T_{max}$ hart auf Null fadet:$$D_{space}(d) = \exp\left(-\frac{d}{\lambda}\right)$$$$D_{time}(t) = \max\left(0, 1 - \frac{t}{T_{max}}\right)$$3.3 Multi-Wave Interference im Fragment ShaderWenn mehrere Einschläge existieren, müssen ihre Amplituden im Fragment Shader akkumuliert werden. Da Wellen sich additiv verhalten (Konstruktive Interferenz), werden die Intensitäten der einzelnen Ripples summiert.OpenGL Shading Language// Array zur Aufnahme multipler Einschläge (Erklärung der Limitierung im Architekturteil)
const int MAX_IMPACTS = 4;
// Format: vec4(localX, localY, localZ, timeSinceHit)
// timeSinceHit < 0.0 bedeutet, dieser Slot ist aktuell inaktiv.
uniform vec4 u_Impacts[MAX_IMPAcripts]; 

// Vom Vertex Shader interpoliert
in vec3 v_LocalPos; 

float calculateRippleIntensity(vec3 fragPos, vec4 impactData) {
    float timeSinceHit = impactData.w;
    // Early-Exit zur Schonung der Fragment-ALU
    if (timeSinceHit < 0.0) return 0.0; 
    
    vec3 impactPos = impactData.xyz;
    float dist = length(fragPos - impactPos);
    
    // Konstanten für die physikalische Simulation
    const float WAVE_SPEED = 18.0;      // Ausbreitungsgeschwindigkeit
    const float WAVE_WIDTH = 2.5;       // Schärfe/Dicke des Rings (höher = dünner)
    const float MAX_DISTANCE = 25.0;    // Räumliches Abklingen
    const float MAX_DURATION = 1.5;     // Lebensdauer in Sekunden
    
    // Position der Wellenfront
    float currentRadius = timeSinceHit * WAVE_SPEED;
    float distFromRadius = abs(dist - currentRadius);
    
    // Gaußscher Ring
    float waveShape = exp(-(distFromRadius * distFromRadius) * WAVE_WIDTH);
    
    // Dämpfungsfaktoren
    float spatialDecay = exp(-dist / (MAX_DISTANCE * 0.4));
    float temporalDecay = max(0.0, 1.0 - (timeSinceHit / MAX_DURATION));
    
    // Nur Fragmente berücksichtigen, die die Welle bereits erreicht hat, 
    // um "implodierende" Artefakte am Ursprung zu vermeiden
    float directionalMask = step(0.0, currentRadius - dist + 2.0);
    
    return waveShape * spatialDecay * temporalDecay * directionalMask;
}
Die finale Verknüpfung von Basis-Farbe (Energie) und Ripple-Intensität erzeugt einen additiven Overdrive-Effekt (Hit-Flash), der das Hexagon-Muster an der Einschlagstelle stark weiß aufleuchten lässt und die Transparenz lokal massiv erhöht.OpenGL Shading Languagevoid main() {
    vec3 baseColor = calculateEnergyColor(u_EnergyLevel, u_GameTime);
    float hexAlpha = generateProceduralHexagons(v_LocalPos); // Vorhandene Funktion
    
    float totalRipple = 0.0;
    // Loop Unrolling wird meist vom Shader-Compiler automatisch durchgeführt
    for(int i = 0; i < MAX_IMPACTS; i++) {
        totalRipple += calculateRippleIntensity(v_LocalPos, u_Impacts[i]);
    }
    
    // Clamping, um Clipping-Artefakte in der Farb-Mathematik zu verhindern
    totalRipple = clamp(totalRipple, 0.0, 2.0); 
    
    // Der Ripple verschiebt die Farbe ins Weiße (Übersteuerung)
    vec3 finalColor = mix(baseColor, vec3(1.0, 1.0, 1.0), min(totalRipple * 0.7, 1.0));
    
    // Der Ripple macht das Schild an der Stelle temporär undurchsichtiger
    float finalAlpha = clamp(hexAlpha + (totalRipple * 0.6), 0.0, 1.0);
    
    fragColor = vec4(finalColor, finalAlpha);
}

Event-Synchronisation und Netzwerk-Schicht (NeoForge 1.21)Ein Schildeinschlag ist ein ephemeres (flüchtiges) Ereignis. Die autoritative Berechnung des Schadens findet auf dem logischen Server im SpaceshipShieldHandler statt. Das View-Modell des Clients (ClientShipState) hat keinerlei Kenntnis von der Projektil-Physik oder den Explosionen des Servers. Folglich muss der Server ein hochperformantes Netzwerk-Event auslösen, welches den Client über Position und Zeitpunkt des Treffers informiert.NeoForge 1.21 markiert einen radikalen Paradigmenwechsel in der Netzwerk-Architektur von Minecraft. Legacy-Paketsysteme wurden vollständig durch deklarative CustomPacketPayloads und bidirektionale StreamCodecs ersetzt, um typsichere und thread-sichere Serialisierung zu erzwingen.5.1 Design des ShipImpactEventPayloadUm das Netzwerk nicht durch redundante Daten aufzublähen, muss das Payload-Record extrem schlank konzipiert werden. Benötigt werden exakt drei Informationsblöcke:Die Identifikation des betroffenen Raumschiffs (UUID).Die relative Einschlagposition (Vec3 im Local-Space).Die kinetische Stärke des Treffers (ein Float, der die Amplitude des Ripples skalieren könnte, optional).Die Serialisierung in NeoForge 1.21 bedient sich vordefinierter ByteBufCodecs. Da Vec3 nicht immer standardmäßig als einzelner Codec vorliegt, wird es elegant in seine drei primitiven Double-Komponenten zerlegt, um Robustheit zu garantieren. Das UUIDUtil stellt zudem einen dedizierten StreamCodec für UUIDs bereit.Javapackage com.peaceman.alpha.network;

6. Client-Lifecycle, View-Model und VRAM-ManagementSobald das Netzwerkpaket den Client erreicht, übernimmt der ClientPayloadHandler. Minecraft verbietet strikt die Modifikation von Rendering-Datenstrukturen außerhalb des Main-Threads (Render-Thread). Daher muss das Paket zwingend via context.enqueueWork() an die Hauptschleife übergeben werden, bevor der ClientShipManager das zugehörige ClientShipState aufruft.6.1 Ring-Buffer-Implementierung im ClientShipStateDas ClientShipState verwaltet das compilierte VBO (VertexBuffer) des Schildes. Um die Multi-Impacts zu verwalten, ohne Speicherallokationen (Garbage Collection Spikes) im Render-Loop zu provozieren, wird ein primitiver Arrays-basierter Ring-Buffer implementiert.Dieser Ring-Buffer hält konstant 4 Positionen und 4 Zeitstempel. Bei einem neuen Einschlag überschreibt der Cursor iterativ den ältesten Slot.Javapackage com.peaceman.alpha.client.state;

import net.minecraft.world.phys.Vec3;
import com.mojang.blaze3d.vertex.VertexBuffer;
import net.minecraft.client.renderer.ShaderProgram;
import java.util.UUID;
// ... weitere Imports ...

public class ClientShipState {
    private final UUID shipId;
    private VertexBuffer shieldMesh;
    
    // Zero-Allocation Ring-Buffer für O(1) Updates
    private static final int MAX_IMPACTS = 4;
    private final Vec3[] impactPositions = new Vec3[MAX_IMPACTS];
    private final long[] impactTickTimes = new long[MAX_IMPACTS];
    private int impactCursor = 0;
    
    public ClientShipState(UUID shipId) {
        this.shipId = shipId;
        // Initialisierung mit Werten, die den Shader den Slot als inaktiv werten lassen
        for (int i = 0; i < MAX_IMPACTS; i++) {
            impactTickTimes[i] = -1000; 
            impactPositions[i] = Vec3.ZERO;
        }
    }
    
    public void addImpact(Vec3 localPos, long currentClientTick) {
        impactPositions[impactCursor] = localPos;
        impactTickTimes[impactCursor] = currentClientTick;
        // Zyklisches Weiterschalten des Cursors
        impactCursor = (impactCursor + 1) % MAX_IMPACTS;
    }
    
    // Pushing der Uniforms direkt vor dem Draw-Call
    public void setupShaderUniforms(ShaderProgram shader, long currentTick, float partialTicks) {
        float exactTime = currentTick + partialTicks;
        
        for (int i = 0; i < MAX_IMPACTS; i++) {
            String uniformName = "u_Impact" + i;
            long hitTick = impactTickTimes[i];
            
            float timeSinceHit = -1.0f; // < 0.0 bedeutet inaktiv im GLSL
            
            // Wenn der Treffer nicht älter als 100 Ticks (5 Sekunden) ist
            if (hitTick > 0 && (currentTick - hitTick) < 100) { 
                timeSinceHit = (exactTime - hitTick) / 20.0f; 
            }
            
            // Bindung an den Shader, sofern die Uniform vom Compiler nicht wegoptimiert wurde
            if (shader.getUniform(uniformName) != null) {
                shader.getUniform(uniformName).set(
                    (float)impactPositions[i].x, 
                    (float)impactPositions[i].y, 
                    (float)impactPositions[i].z, 
                    timeSinceHit
                );
            }
        }
    }
}

    for (ClientShipState ship : ClientShipManager.getAllShips()) {
        if (!ship.isShieldActive() || ship.isDisposed()) continue;
        
        stack.pushPose();
        // Transformation in den Local-Space des Schiffes
        translateToAnchor(stack, ship.getAnchorPos(), camera);
        
        // Globale Energie-Uniform übermitteln
        if (shieldShader.getUniform("u_EnergyLevel") != null) {
            shieldShader.getUniform("u_EnergyLevel").set(ship.getShieldEnergyPercentage());
        }
        
        // Die 4 Impact-Vektoren aus dem Ring-Buffer binden
        ship.setupShaderUniforms(shieldShader, currentTick, partialTicks);
        
        VertexBuffer mesh = ship.getShieldMesh();
        mesh.bind();
        
        // Draw-Call mit aktueller Projektionsmatrix (1.21 Syntax)
        mesh.drawWithShader(stack.last().pose(), RenderSystem.getProjectionMatrix(), shieldShader); [cite: 6, 8]
        
        VertexBuffer.unbind();
        stack.popPose();
    }
}
Kritischer Aspekt: VRAM Leak Prevention.
Da VertexBuffer-Instanzen direkten Grafikspeicher belegen, führt das Zerstören eines Schiffes oder das Verlassen des Chunks zu einem katastrophalen Memory Leak, wenn das VBO nicht freigegeben wird. Der ClientShipManager überwacht die Events ChunkEvent.Unload und ClientPlayerNetworkEvent.LoggingOut. Beim Eintreten dieser Events ruft er ship.dispose() auf. Dort muss mesh.close() in einem dedizierten RenderSystem.recordRenderCall(...) gewrappt werden, um sicherzustellen, dass die Speicherfreigabe synchronisiert auf dem OpenGL-Kontext-Thread abläuft.
