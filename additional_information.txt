Audit-Report: Deep Validation & Code Review der NeoForge 1.21 Raumschiff-KollisionsarchitekturArchitektonische Einführung und SystemkontextDie Entwicklung eines performanten, Voxel-basierten Raumschiff-Kollisionssystems für Minecraft NeoForge 1.21 stellt eine signifikante ingenieurtechnische Herausforderung dar. Klassische physikalische Simulationen greifen bei Voxel-Gittern oft auf diskrete Kollisionserkennung (Discrete Collision Detection, DCD) zurück, bei der Objekte in festen Zeitintervallen auf Überschneidungen geprüft werden. Bei hohen Translationsgeschwindigkeiten – wie sie Raumschiffe in der vorliegenden Modifikation erreichen können – versagt dieser Ansatz jedoch aufgrund des sogenannten High-Speed-Tunneling-Effekts. Dabei durchdringen Objekte einander zwischen zwei Server-Ticks vollständig, ohne dass eine Kollision registriert wird.Das vorliegende System adressiert dieses Problem korrekt durch die Implementierung von Continuous Collision Detection (CCD) mittels Swept-AABBs (Axis-Aligned Bounding Boxes) in der Broad-Phase. Die anschließende Narrow-Phase nutzt linearisierte BitSet-Strukturen zur Extraktion von Voxel-Subvolumina, was hochperformante Schnittpunktberechnungen auf Hardware-Ebene (durch bitweise AND-Operationen) ermöglicht. Obwohl diese konzeptionelle Basis mathematisch solide ist, offenbart die tiefergehende Validierung der Klassen ShipCollisionService.java und CollisionResolver.java kritische Engpässe in der Speicherallokation, der Netzwerksynchronisation, der physikalischen Logik-Auflösung sowie der Handhabung von Vektor-Clamping.Der folgende Audit-Report analysiert diese Systemkomponenten in extremer Detailtiefe, leitet zweite und dritte Ordnungen der architektonischen Auswirkungen ab und liefert produktionsreife Implementierungsstrategien für die identifizierten Schwachstellen.1. Performance-Metriken und Object Churn in der Server-Tick-SchleifeDie Skalierbarkeit eines synchronen Multiplayer-Servers in der Minecraft-Engine wird maßgeblich durch zwei limitierende Faktoren bestimmt: den Garbage Collector (GC) der Java Virtual Machine (JVM) und die Bandbreitenkapazität des Netty-basierten Network-Threads. Das absolute Zeitbudget eines Server-Ticks zur Aufrechterhaltung von 20 Ticks per Second (TPS) liegt bei exakt 50 Millisekunden. Jede Architektur, die in diesem kritischen Pfad operiert, muss deterministische Ausführungszeiten und einen minimalen Speicher-Footprint garantieren.1.1 Die Allokationslast der BitSet-Strukturen in der Narrow-PhaseIn der Methode ShipCollisionService.extractSubVolumeBitSet() wird für jedes Schiff, das an einer potenziellen Kollision teilnimmt, eine neue Instanz der Klasse BitSet erstellt, deren Größe durch das Volumen der Intersection-AABB definiert ist (totalVolume).Die zugrundeliegende Mechanik dieses Ansatzes ist tückisch, da sie bei kleinen Raumschiffen performant erscheint, bei massiven Voxel-Konstrukten jedoch exponentiell degradiert. Wenn zwei gewaltige Mutterschiffe aneinander entlang gleiten, kann die Broad-Phase-Intersection-Box leicht Dimensionen von 64x64x64 Blöcken erreichen. Dies resultiert in einem totalVolume von 262.144 Voxeln pro Schiff. Die BitSet-Klasse der Java-Standardbibliothek allokiert intern ein long[]-Array, um diese Bits zu speichern. Für 262.144 Bits werden 4.096 long-Werte benötigt, was einem Speicherbedarf von exakt 32 Kilobyte (KB) pro Array entspricht.Die Auswirkungen zweiter und dritter Ordnung dieser Allokationsstrategie sind gravierend. Werden in einem einzigen Server-Tick auf einem dicht besiedelten Server 20 potenzielle Kollisionen geprüft, generiert das System 40 solcher BitSet-Instanzen. Dies entspricht einer Allokation von 1,28 Megabyte pro Tick, was sich über eine Laufzeit von einer Minute auf über 1,5 Gigabyte summiert. Moderne Garbage Collectoren wie der G1GC (Garbage-First) oder ZGC sind zwar in der Lage, Kurzzeit-Objekte in der Eden-Space-Generation effizient zu bereinigen, jedoch führt dieser massive "Object Churn" zu einem extremen Durchsatz in den Thread-Local Allocation Buffers (TLABs). Wenn TLABs erschöpft sind, muss die JVM neue Puffer allozieren, was unweigerlich zu Micro-Pauses im Main-Thread führt. Überschreiten die internen long[]-Arrays eine gewisse Schwellengröße, werden sie vom G1GC als "Humongous Objects" klassifiziert und direkt in die Old Generation geschrieben, was vorzeitige Major GCs (Stop-The-World-Pausen) erzwingt und zu katastrophalen TPS-Einbrüchen führt.Voxel-Dimensionen der IntersectionBenötigte Bits (totalVolume)Speicherbedarf pro BitSet (KB)Allokation bei 20 Kollisionen/Tick (MB/s)Klassifizierung (G1GC Tendenz)16 x 16 x 164.096~0,5~0,02Eden Space (Regulär)32 x 32 x 3232.768~4,0~0,16Eden Space (Regulär)64 x 64 x 64262.144~32,0~1,28Eden Space (Erhöhte TLAB-Auslastung)128 x 128 x 1282.097.152~256,0~10,24Humongous Object (Kritisch)Optimierung: Implementierung von ThreadLocal BitSet-PoolingDa die physikalische Auswertung des Minecraft-Server-Ticks primär Single-Threaded auf dem Main-Thread abläuft, ist die fortlaufende Instanziierung von neuen Objekten für Kurzzeit-Kollisionsprüfungen eine erhebliche Verschwendung von JVM-Ressourcen.     private static void fillSubVolumeBitSet(BitSet bitSet, VoxelGridCache cache, BlockPos origin, int minX, int minY, int minZ, int width, int height, int depth) {
        for (int x = 0; x < width; x++) {
            int relX = (minX + x) - origin.getX();
            for (int y = 0; y < height; y++) {
                int relY = (minY + y) - origin.getY();
                for (int z = 0; z < depth; z++) {
                    int relZ = (minZ + z) - origin.getZ();

                    if (cache.isSet(relX, relY, relZ)) {
                        int index = x + (y * width) + (z * width * height);
                        bitSet.set(index);
                    }
                }
            }
        }

3. Mathematische Präzision und Speichersicherheit in der Narrow-PhaseDie Architektur stützt sich auf ein zweistufiges Filtersystem. Zunächst erzeugt die Broad-Phase eine Sweep-Bounding-Box und ermittelt bei Überschneidung das exakte Schnittvolumen (Intersection-Volume). Anschließend extrahiert die Narrow-Phase die Voxel-Daten aus diesem Raum in lineare Datenstrukturen. Jeder mathematische Fehler in diesem Pfad führt zu irreparablen Engine-Crashes.3.1 Die 3D-zu-1D Flattening-FormelDie Index-Zuweisung für die Befüllung des BitSet lautet:$index = x + (y \cdot width) + (z \cdot width \cdot height)$Diese mathematische Konvention (auch als Row-Major-Order oder Z-Order Flattening bekannt) ist zu 100 % valide und bildet ein dreidimensionales kartesisches Koordinatensystem lückenlos in einen linearen, eindimensionalen Adressraum ab. Solange die Integrität der Grenzen ($x < width$, $y < height$ und $z < depth$) durch die Iterationsschleifen respektiert wird, entstehen keine Index-Kollisionen, und der maximale berechnete Index terminiert exakt bei $(width \cdot height \cdot depth) - 1$. Da das Array mit einer Länge von $totalVolume$ instanziiert wird, sind Out-of-Bounds-Fehler auf Seiten des BitSet mathematisch ausgeschlossen. Zusätzlich bietet diese lineare Anordnung enorme Vorteile für die Cache-Lokalität der CPU beim späteren Hardware-ANDing.3.2 Floating-Point Drift und Cache Out-of-BoundsKritischer Fund: Gleitkomma-Drift in der Array-ExtraktionDie Broad-Phase reicht eine fließkommabasierte Bounding-Box in die Narrow-Phase weiter. Die Klasse transformiert diese Box in Integer-Koordinaten:Javaint minX = (int) Math.floor(intersectionBox.minX);
int maxX = (int) Math.ceil(intersectionBox.maxX);
Dieses vermeintlich triviale Casting verbirgt eine massive Gefahr, die auf dem IEEE 754 Standard für Gleitkomma-Arithmetik basiert. In der Physik-Laufzeitumgebung kann ein normalisierter Vektor dazu führen, dass intersectionBox.maxX exakt auf einer theoretischen Block-Grenze berechnet wird, beispielsweise 12.0. Durch marginalste Rundungsfehler bei Multiplikationen (Floating-Point Drift) wird dieser Wert zu 12.000000000001. Die Funktion Math.ceil() ist gnadenlos und transformiert diesen Wert sofort zu 13. Die extrahierte AABB wächst artifiziell um einen ganzen Block an.Das fatale Edge-Case-Szenario ereignet sich in der innersten Schleife:Javaint relX = worldX - origin.getX();
if (cache.isSet(relX, relY, relZ)) { ... }
Wenn die Intersection-AABB durch den Fließkomma-Drift aus den eigentlichen Dimensionen des Voxel-Schiffes hinauswächst, wird der berechnete Index relX, relY oder relZ die physischen Ausmaße des Schiffes überschreiten. Der "Clamping"-Edge-Case: Swept-AABB und Time of Impact (TOI)Die Auflösung einer positiven Kollisionsprüfung im CollisionResolver führt in den Fällen 1, 2 und 4 zu einem abrupten kinetischen Stopp. Das System kommuniziert diesen Stopp, indem es Vec3.ZERO als den "geclampten" (zurückgeschnittenen) Bewegungsvektor in der CollisionResolution an das übergeordnete System übergibt.4.1 Analyse des statischen Gap-Phänomens (Lückenbildung)Kritischer Fund: Physikalische Stase und Immersion-BreakDie statische Zuweisung clampedVector = Vec3.ZERO bedeutet aus der Perspektive der Physik-Simulation: Das Schiff hat sich während dieses Server-Ticks überhaupt nicht bewegt.Zur Veranschaulichung des resultierenden Fehlers: Schiff A propagiert einen Bewegungsvektor von (10, 0, 0) pro Tick. Es befindet sich exakt 8 Blöcke von der statischen Hülle von Schiff B entfernt. Die Swept-AABB-Funktion extrapoliert das künftige Volumen für die volle Distanz von 10 Blöcken. Die Broad-Phase meldet eine Überschneidung der Boxen. Die Narrow-Phase bestätigt den voxelgenauen Kontakt. Der Resolver triggert den Stopp und gibt Vec3.ZERO zurück.
Das fatale Resultat: Schiff A bewegt sich keinen Millimeter. Es verbleibt auf seiner Initialposition (0). Zwischen den Schiffen A und B klafft eine optische Lücke von 8 Blöcken. Obwohl die Engine die Kollision evaluiert, die Schilde abbaut und Explosionen generiert, frieren die Modelle in der Luft ein, völlig unverbunden. Dies dekonstruiert jede visuelle und physikalische Plausibilität in einem Swept-AABB-System, dessen gesamter Daseinszweck eigentlich darin besteht, exakte Treffer bei hohen Geschwindigkeiten zu simulieren.4.2 Lösungsarchitektur: Berechnung des Time of Impact (TOI)Um High-Speed-Tunneling elegant mit einer physikalischen Stopp-Reaktion zu verheiraten, muss der Algorithmus den sogenannten Time of Impact (TOI) (Kollisionszeitpunkt) ermitteln. Der TOI ist ein skalarer Bruchteil ($t$), der exakt definiert, wie viel Prozent des Bewegungsvektors zurückgelegt wurden, bevor die Volumina der Objekte erstmals interagieren ($0.0 \le t \le 1.0$).Die Berechnung des TOI beruht auf der Minkowski-Differenz (Minkowski Sum). Für 3D-Swept-AABBs wird die Entry-Distanz (der Abstand zwischen der Front des bewegten Objekts und der Rückseite des statischen Ziels) geteilt durch die Geschwindigkeit (Velocity) auf der jeweiligen kartesischen Achse evaluiert. Wenn die Kollision im obigen Beispiel nach 8 von 10 Blöcken auftritt, ist $t = 0.8$. Der korrekte, gekürzte Vektor lautet dann movementVector.scale(0.8). Um ständiges Re-Kollidieren (Z-Fighting auf Physik-Ebene) im nächsten Engine-Tick zu verhindern, wird ein infinitesimaler Toleranzwert (Epsilon) abgezogen: movementVector.scale(Math.max(0, t - epsilon)).Ursprungsvektor (Distanz/Tick)Reale Distanz bis KontaktTOI (t)Korrekter clampedVectorEffekt im Spiel(10, 0, 0)8.0 Blöcke0.80(8, 0, 0)Visuell perfekter Kontakt an Blockgrenze(0, -20, 0)5.0 Blöcke0.25(0, -5, 0)Sanftes Aufsetzen bei Sturzflug(15, 0, 0)15.0 Blöcke1.00(15, 0, 0)Bewegung abgeschlossen, Berührung im nächsten TickCode-Fix: Voxelgenaue Vektor-Skalierung mittels Swept-TOIDie Standard-Algorithmik in C/Python für Swept-AABBs kann in Java übersetzt werden, um den TOI direkt aus den Bounding-Boxen der kollidierenden Voxel-Gitter abzuleiten. Diese Methode sollte in den ShipCollisionService implementiert und vom Resolver aufgerufen werden.Java// Hilfsmethode im ShipCollisionService basierend auf Swept AABB TOI-Algorithmen
public static double calculateTimeOfImpact(AABB movingBox, AABB targetBox, Vec3 velocity) {
    double tEntryX = -Double.MAX_VALUE, tExitX = Double.MAX_VALUE;
    double tEntryY = -Double.MAX_VALUE, tExitY = Double.MAX_VALUE;
    double tEntryZ = -Double.MAX_VALUE, tExitZ = Double.MAX_VALUE;

    // Berechnung auf der X-Achse
    if (velocity.x > 0) {
        tEntryX = (targetBox.minX - movingBox.maxX) / velocity.x;
        tExitX = (targetBox.maxX - movingBox.minX) / velocity.x;
    } else if (velocity.x < 0) {
        tEntryX = (targetBox.maxX - movingBox.minX) / velocity.x;
        tExitX = (targetBox.minX - movingBox.maxX) / velocity.x;
    } else {
        if (movingBox.maxX <= targetBox.minX || movingBox.minX >= targetBox.maxX) return 1.0;
    }

    // Berechnung auf der Y-Achse
    if (velocity.y > 0) {
        tEntryY = (targetBox.minY - movingBox.maxY) / velocity.y;
        tExitY = (targetBox.maxY - movingBox.minY) / velocity.y;
    } else if (velocity.y < 0) {
        tEntryY = (targetBox.maxY - movingBox.minY) / velocity.y;
        tExitY = (targetBox.minY - movingBox.maxY) / velocity.y;
    } else {
        if (movingBox.maxY <= targetBox.minY || movingBox.minY >= targetBox.maxY) return 1.0;
    }

    // Berechnung auf der Z-Achse
    if (velocity.z > 0) {
        tEntryZ = (targetBox.minZ - movingBox.maxZ) / velocity.z;
        tExitZ = (targetBox.maxZ - movingBox.minZ) / velocity.z;
    } else if (velocity.z < 0) {
        tEntryZ = (targetBox.maxZ - movingBox.minZ) / velocity.z;
        tExitZ = (targetBox.minZ - movingBox.maxZ) / velocity.z;
    } else {
        if (movingBox.maxZ <= targetBox.minZ || movingBox.minZ >= targetBox.maxZ) return 1.0;
    }

    // Der Startzeitpunkt der 3D-Kollision ist das Maximum aller Einrittszeiten auf den Einzelachsen.
    double tEntry = Math.max(tEntryX, Math.max(tEntryY, tEntryZ));
    double tExit = Math.min(tExitX, Math.min(tExitY, tExitZ));
    
    // Validierung: Wenn keine Überschneidung stattfand oder der Vektor in die falsche Richtung zeigt
    if (tEntry > tExit || (tEntryX < 0 && tEntryY < 0 && tEntryZ < 0) || tEntry > 1.0) {
        return 1.0; 
    }
    
    return Math.max(0.0, tEntry);
}

Synthetisierendes Fazit und Architekturelle ImperativeDie vorliegende Evaluierung der NeoForge 1.21 Raumschiff-Kollisionsarchitektur bestätigt, dass die Transition von diskreter zu kontinuierlicher Kollisionserkennung (Swept-AABB) in Voxel-Umgebungen ein ambitionierter und korrekter Ansatz ist. Die zugrundeliegenden mathematischen Flattening-Algorithmen und die Nutzung von BitSets für hardwarenahe boolesche Operationen zeugen von einem tiefen Verständnis für die Limitierungen der Engine. Dennoch erfordern die identifizierten Umsetzungslücken zwingende Eingriffe, um die Architektur von einem funktionalen Prototyp in ein produktionsbereites Multi-User-System zu überführen.Der unkontrollierte Speicher-Overhead durch temporäre BitSets und die exponentielle Bandbreitenverschwendung bei der monolithischen Netzwerksynchronisation sind keine bloßen Schönheitsfehler. Sie sind garantierte Vektoren für katastrophale Server-Timeouts unter realer Multiplayer-Last. Die verbindliche Integration von Thread-lokalem Object-Pooling und NeoForge-konformen Delta-Payloads für Voxel-Modifikationen wird die TPS-Stabilität des Servers dramatisch konsolidieren.Darüber hinaus stellen die Asynchronitäten im Bohrer-Modus (Fall 3) ein ernstzunehmendes Risiko für die Gameplay-Integrität dar. Die Physik-Engine von Minecraft kann gigantische, Entity-umschließende Matrix-Strukturen nicht in Hochgeschwindigkeitsteleportationen verschieben, ohne Kollisions-Artefakte (Suffocation) zu generieren. Die Zerstückelung des Translationsvektors in Mikroschritte auf der Ebene des Movement-Services ist hier die einzig logische Antwort.Schlussendlich demaskiert die Clamping-Logik mit Vec3.ZERO ein eklatantes Versäumnis in der Handhabung der Endzustände. Ohne die mathematisch korrekte Skalierung des Vektors anhand des Time of Impact (TOI) ist das System blind für die verbleibende Restkinetik. Die Extrapolation des TOI wird den Sprung von einer statischen Ja/Nein-Kollisionsabfrage hin zu einem fließenden, physikalisch plastischen Ramm-Manöver ermöglichen und die Systemstabilität und visuelle Kohärenz der Modifikation auf Enterprise-Level heben.
